# 一期一会 — 作り直しの設計方針

> 状態：方針合意済み（実装方法は未定）
> 目的：核のアイデア「過去の写真と同じ場所で撮ると、メッセージが読める」に沿って、機能とルールを絞り込む

---

## 1. 基本の考え方

- **1人でも楽しめる**こと（過去の自分に会いに行く追体験アプリ）を必ず満たす。共有はその延長として成り立たせる
- 期限や自動削除のような「時間で状態が変わるルール」を持たない。状態はユーザーの操作（封をする、解除する）でだけ変わる
- ロックの判定はすべてサーバー側で行う。アプリ側の表示制御だけに頼らない

---

## 2. 中心となる概念

| 概念 | 中身 |
|---|---|
| **思い出** | 写真、場所、撮影日時と、そこに積み重なるメッセージの集まり |
| **メッセージ** | 元のメッセージと、その後の追記。どれも「下書き」か「封をした」状態を持つ |
| **アルバム** | 思い出を入れるフォルダ。1階層のみ。共有の単位を兼ねる |
| **解除** | ある人がある思い出を、現地で解除した記録（日時つき） |

### 旧設計からの置き換え

| 旧 | 新 |
|---|---|
| 現像待ち（3日で自動削除） | 下書き。期限なし |
| 机の上 | 「未整理」。アルバムに入っていない思い出が並ぶだけで、専用の仕組みは持たない |
| アルバム | そのまま |
| 本棚 | 廃止（必要になったら再検討） |
| 撮影から3日は編集可 | 封をするまではいつでも編集可 |
| 解除は7日間有効 | 解除した時点までの内容はずっと読める |
| 訪問記録・相互表示・写真追加の許可 | 「追記」に一本化 |

---

## 3. ロックのルール

### 3.1 封をする
- 撮影直後のメッセージは**下書き**。自分だけが読めて、いつでも書き直せる
- ユーザーが好きなタイミングで**封をする**と、そのメッセージには鍵がかかる
- 封をした後は、**自分も含めて**誰も現地で解除しない限り読めない
- 封をする操作は**現地でなくてもよい**（元のメッセージ、追記とも）

### 3.2 解除する
- 条件：撮影地点の近く（GPS）で撮影し、AI が同じ場所と判定すること
- 解除すると、**その時点までに封をされたメッセージ**がすべて読めるようになり、以後ずっと読める
- 解除の後に封をされたメッセージは、**もう一度現地で解除するまで読めない**
- **封をした当日の解除では読めない**。封をした日の翌日以降の解除で読めるようになる（現地で封をしてその場で解除し直す抜け道を防ぐ）
  - 日付の区切りは、利用者の端末のタイムゾーンで判定する

### 3.3 追記する
- その思い出を解除したことのある人は、追記を書ける
- 追記も下書きから始まり、封をすると鍵がかかる
- **自分の追記も、次に訪れるまで読めない**
- 書く場所・封をする場所は現地でなくてもよい

### 3.4 体験の流れ（例）

1. 春：Aさんが撮影し、家でメッセージに封をする
2. 夏：Bさんが現地で解除し、Aさんのメッセージを読む。帰り道に追記して封をする
3. 秋：Aさんが再訪して解除し、Bさんの追記を読む。さらに追記して封をする
4. Bさんは秋の追記を読むため、また現地へ行く

1人で使う場合も同じで、「解除して読む → 追記して封をする → 次の訪問で過去の自分の追記に会う」が繰り返される。

### 3.5 訪問写真
- 解除のときに撮った写真は、**保存するかを選べる**
- 保存した写真は「訪問写真」として、その思い出に時系列で積み重なる（元の写真 → 1回目の訪問 → 2回目の訪問…）
- 判定はおおまかに行うので、季節や年月による風景の変化を並べて楽しめる
- 訪問写真は、解除の記録に写真を任意で添えたものとして扱う（新しい概念は増やさない）

---

## 4. 共有

### 4.1 友人間の共有（最初から作る）
- アルバム単位で、招待リンクからメンバーを招く
- メンバーは思い出の追加と追記ができる（共同アルバム）
- **下書きはメンバーに見えない**。封をした時点で、共有アルバムに写真が現れる
- 写真そのものはメンバー全員に見える（宝の地図の役割）。メッセージだけがロックされる
- **共有アルバムから思い出を外すと、他のメンバーは写真もメッセージも見えなくなる**。すでに解除済みのメンバーも読めなくなる
- **再び共有アルバムに入れると、以前解除したメンバーはまた読める**
  - 外しても解除の記録は消さない。「今その思い出を見られる人」のうち、解除の条件を満たす人が読める、と毎回判定する
  - アルバムを抜けたメンバーが戻ってきた場合も、同じルールで読めるようになる

### 4.2 メンバーの役割

| 役割 | できること | 使う時期 |
|---|---|---|
| 持ち主 | すべて（招待、メンバー管理、アルバム削除を含む） | 最初から |
| 編集者 | 思い出の追加、追記 | 最初から |
| 参加者 | 追記のみ | 将来（イベント） |

最初は持ち主と編集者だけを使う。役割の欄は、将来のイベントでデータの形を変えずに済むよう、最初から持たせておく。

### 4.3 将来：イベント（後回し）
- 主催者が作ったアルバムを、参加者が読み取り専用で辿る
- 参加者は追記だけできる、という形を想定
- 大人数になったときの追記の見え方（全員に見せるか、主催者にだけ届けるか）は、その段階で決める

## 5. 画面構成（案）

| 画面 | 役割 |
|---|---|
| マップ | 自分と共有アルバムの、封をした思い出を地図に表示。解除の入口 |
| 撮影 | 写真を撮る。そのまま下書きを書いてもよい |
| 思い出一覧 | 未整理とアルバムの一覧。下書きの編集と封をする操作もここから |
| 思い出の詳細 | 写真、読めるメッセージ、ロック中のメッセージの数、追記の作成 |
| 解除カメラ | 現地で撮影して解除する |
| 設定 | 表示名、ログアウトなど |

## 6. 後回しにするもの

- タイムカプセル（開封日の指定と通知）。最初に戻す候補
- 本棚
- カメラロール保存の設定
- 課金（写真枚数の上限、魔法の鍵）
- イベント機能

## 7. 写真の保存量

- 下書きも含めた**写真の合計枚数**に上限を設ける。下書き専用の制限や期限は設けない
- 数え方は「容量（MB）」ではなく「枚数」とする（利用者に分かりやすいため）
- 上限は**今持っている枚数**で数える。写真を消せば枠が空く
- 共有アルバムに追加した写真は、追加した人の枚数に数える
- 保存した訪問写真は、撮った人の枚数に数える。保存しなかった解除の写真は判定にだけ使い、枚数に数えない
